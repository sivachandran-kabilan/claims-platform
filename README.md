# APAC Claims Platform

Claims platform for a multi-market insurer: motor and property claims across Singapore, Australia, Hong Kong, Malaysia, Thailand and the Philippines. Built as a 5-hour assessment.

- **Claimants** register, report incidents, track their claims, answer information requests and receive notifications.
- **Claims staff** pick up claims, assess (reserve), request information, approve or reject, and record settlement.
- **Claims managers** see team workload and outstanding liability exposure, act on any claim, and create staff accounts.

**Stack:** .NET 8 (ASP.NET Core controllers, EF Core 8, ASP.NET Core Identity, MediatR 12, FluentValidation 12), SQL Server, Kafka 4.3 (KRaft, Docker) via Confluent.Kafka, Angular 22 (standalone, signals) with a client generated by ng-openapi-gen. Tests: xUnit, FluentAssertions 7, NSubstitute, `WebApplicationFactory`.

**Read next:** design decisions in [`docs/adr/`](docs/adr), the current-state knowledge base in [`docs/knowledge/`](docs/knowledge), and the AI working journal in [`docs/journal.md`](docs/journal.md) (raw prompts: [`docs/prompt-log.md`](docs/prompt-log.md)).

## Architecture

A **modular monolith** (ADR 001): one deployable with Clean Architecture layers and two modules (Claims, Identity) sharing one `DbContext`, so a claim change and its event commit in one transaction.

```
                    ┌──────────────── Claims.Api ────────────────┐
 Angular (web/) ──► │ Controllers (HTTP → MediatR only), JWT,     │
  REST + JWT        │ policies, ProblemDetails, rate limiting     │
                    └───────────────┬────────────────────────────┘
                                    ▼
                    ┌──────────── Claims.Application ────────────┐
                    │ Vertical slices: Command/Query + Validator  │
                    │ + Handler. ClaimWorkflow runs every action: │
                    │ 428 → 404 → 403 → 412 → domain → save       │
                    │ Ports: IClaimsDbContext, IIdentityService,  │
                    │ IReportQueries, IEventPublisher, ...        │
                    └───────┬───────────────────────────▲────────┘
                            ▼                           │ implements
                    ┌─── Claims.Domain ───┐   ┌──── Claims.Infrastructure ─────┐
                    │ Claim aggregate     │   │ EF Core + Identity (SQL Server) │
                    │ ClaimTransitions    │   │ SaveChangesAsync → outbox rows  │
                    │ (action-keyed)      │   │ OutboxRelay ──► Kafka ──┐        │
                    │ Money rules, events │   │ NotificationConsumer ◄──┘ (DLT)  │
                    └─────────────────────┘   └─────────────────────────────────┘
```

**One request, end to end** (e.g. `POST /claims/{id}/approve` with `If-Match`):
1. The controller maps HTTP to `ApproveClaimCommand`; FluentValidation rejects bad bodies (400).
2. `ClaimWorkflow` loads the claim filtered by visibility (404 for another claimant's claim), checks who may act (403), and compares the ETag (412).
3. `Claim.Approve()` enforces the money rules (422) and goes through the single private `TransitionTo`, which checks the action-keyed table (409), writes the history row and raises `ClaimDecided`.
4. One `SaveChangesAsync` saves the claim, its history and an `OutboxMessage` in one transaction.
5. The `OutboxRelay` (background) publishes the row to `claims.events` keyed by claim id. The `NotificationConsumer` writes an in-app notification for the claimant (idempotent on `eventId`).

### Key design decisions
| Decision | Why | Where |
|---|---|---|
| **Action-keyed state machine** `(action, status) → status`, one private `TransitionTo`, one endpoint per action, no "set status" | A `(from, to)` table was bypassable: actions share edges | ADR 005, `Claim.cs`, `ClaimTransitions.cs` |
| **Transactional outbox** written in `SaveChangesAsync` | No lost or phantom events; handlers never call Kafka | ADR 003 |
| **Fixed check order** 428 → 404 → 403 → 412 → 409/422 in one runner | Checks can't drift; claimants can't discover other claims; versions can't be probed | ADR 004, `ClaimWorkflow.cs` |
| **ETag = rowversion**; every action stamps `UpdatedAt` | Optimistic concurrency that also covers child-only changes | `ClaimConfigurations.cs` |
| **Money**: currency from market; one currency per claim; approved ≤ reserve; settlement ≤ approved | Simple rules; mixing currencies is impossible; exposure is one column | ADR 006 |
| **Claimant view** hides reserve, outstanding reserve, staff ids and internal history | Reserves are insurer-internal | `ClaimReadModel.cs` |
| **Self-issued JWT** (HS256, 15 min) + fallback "authenticated" policy + explicit role policies | Real auth without an external IdP (non-goal) | ADR 004 |
| **Idempotency-Key** on claim submission; `If-Match` on every action | Safe retries; no duplicate claims | `SubmitClaimCommand.cs` |
| **Reports as SQL `GROUP BY`** behind `IReportQueries` | No aggregates loaded; `DATEDIFF` stays in Infrastructure | `ReportQueries.cs` |

### REST vs Kafka (ADR 002)
- **REST** for every user interaction (register, login, submit, view, every workflow action, reports): the user needs an immediate answer (201, 409, 422, data).
- **Kafka** for facts other components react to, published from the outbox to `claims.events` (key = `claimId`, so per-claim order is kept). Envelope: `eventId, type, version, occurredAt, claimId, payload`, with no PII.

| Event | Raised by | Consumer reaction |
|---|---|---|
| `ClaimSubmitted` | submit | "Your claim … has been received." |
| `InformationRequested` | request-info | "We need more information …" |
| `ClaimDecided` (Approved / Rejected / RejectedNoResponse) | approve, reject, reject-no-response | approved / rejected message |
| `ClaimSettled` | settle | "… has been settled." |

Consumer guarantees: manual offset commit after processing; duplicate `eventId` processed once; 3 tries then `claims.events.dlt` (with error headers); unparseable messages go straight to the DLT. Assign, reassign, reserve and documents raise no events: no consumer needs them, and the audit history records them.

## Run from scratch

### Prerequisites
| Tool | Version used |
|---|---|
| .NET SDK | 8.0.426 (pinned in `global.json`; newer SDKs may be installed side by side) |
| SQL Server | Local default instance (`localhost`), Windows authentication (developed on SQL Server 2025 Developer) |
| Docker Desktop | Engine 29.x, Compose v2+ (Linux containers) |
| Node.js / npm | 24.x / 11.x (web app) |

### Steps
```bash
# 1. Kafka: broker on localhost:9092, topics claims.events + claims.events.dlt, Kafka UI on http://localhost:8080
docker compose up -d

# 2. Tools and packages
dotnet tool restore
dotnet restore

# 3. Configuration in user-secrets (nothing secret is committed)
dotnet user-secrets set "ConnectionStrings:Claims" "Server=localhost;Database=ClaimsPlatformDev;Integrated Security=true;TrustServerCertificate=true" --project src/Claims.Api
dotnet user-secrets set "Jwt:Key" "<random string, at least 32 bytes>" --project src/Claims.Api
#    Dev accounts, seeded at startup in Development only (repeat for Seed:Staff and Seed:Claimant):
dotnet user-secrets set "Seed:Manager:Email" "manager@test.com" --project src/Claims.Api
dotnet user-secrets set "Seed:Manager:Password" "<password, 10+ chars>" --project src/Claims.Api

# 4. Database: schema, the three roles, the claim-number sequence
dotnet ef database update -p src/Claims.Infrastructure -s src/Claims.Api

# 5. API on http://localhost:5000 (Swagger UI at /swagger in Development; "Authorize" with the login token)
dotnet run --project src/Claims.Api

# 6. Web app on http://localhost:4200 (the only origin the API's CORS policy allows)
cd web && npm ci && npx ng serve
```

| URL | What |
|---|---|
| http://localhost:4200 | Web app (claimants → My claims, staff → Queue, managers → Dashboard) |
| http://localhost:5000/swagger | API docs and try-it (Development only) |
| http://localhost:5000/health | Liveness (anonymous) |
| http://localhost:8080 | Kafka UI |

### Dev accounts
In Development the API seeds one account per role from the `Seed:*` user-secrets and never overwrites existing users. The assessment test accounts (`manager@test.com`, `staff@test.com`, `user@test.com`, password = email) are listed in `CLAUDE.md`; they are for local development only. Self-registration always creates a Claimant. Staff and manager accounts are created by a manager via `POST /api/v1/users` (Swagger).

The API refuses to start without a `Jwt:Key` of at least 32 bytes. If migrations are pending, seeding is skipped with a warning.

### Kafka notes
If Kafka is down the API keeps working: outbox rows wait and are published when it is back (verified manually; see journal PROMPT7). Set `Kafka:Enabled=false` to run without a broker (integration tests do). Inspect a topic (in Git Bash, prefix with `MSYS_NO_PATHCONV=1`):
```bash
docker exec claims-kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server kafka:29092 --topic claims.events --from-beginning --property print.key=true
```

### Regenerating the API client
The OpenAPI spec (`docs/openapi.json`) and the generated Angular client (`web/src/app/api/`) are both committed:
```bash
curl -s http://localhost:5000/swagger/v1/swagger.json -o docs/openapi.json   # API running in Development
cd web && npm run gen:api
```

## Security notes
- **Tokens:** self-issued HS256 JWT, 15 minutes, claims `sub, email, role, jti, exp`. Validated for issuer, audience, lifetime, signature and algorithm (HS256 only), with 1-minute clock skew. No refresh token or revocation: a role change applies when the token expires. Production would use an enterprise IdP (Azure AD / OIDC).
- **Login:** identical 401 for unknown email, wrong password and lockout (with a dummy hash check for timing); lockout after 5 failures for 15 minutes; 10 requests/min per IP on register and login. Duplicate registration returns 409, which reveals that an email exists (accepted trade-off).
- **Authorization:** a fallback policy requires authentication everywhere (including unknown URLs: anonymous → 401); every endpoint declares its role policy; resource checks (owner 404, assigned staff 403) run in the application layer. Identity always comes from the token, never the body.
- **Web token storage:** in memory with `sessionStorage` as the reload fallback. Readable by any script on the page (XSS), with damage limited by the 15-minute lifetime. Production: BFF / httpOnly cookie.
- **Data and logs:** secrets only in user-secrets; CORS limited to `http://localhost:4200`; request bodies `application/json` only; errors are RFC 7807 ProblemDetails with no internals; logs record ids and exception types only (no PII, and the framework's exception-message log is disabled).

## Known gaps / with more time
| Area | Gap (shortcut taken) | With more time |
|---|---|---|
| Security | No refresh tokens or revocation; per-IP in-memory rate limit; tiny common-password list; registration 409 enumeration; dev accounts use password = email | IdP (OIDC) with refresh/revocation, a distributed rate limiter, a breached-password check, generic registration responses |
| Security | Staff accounts can't be disabled; no staff-admin UI | Disable/role-change endpoints and a manager admin page |
| Workflow | 15-day no-response rejection is a manual staff action; no approval thresholds; single settlement only | A scheduled sweep, approval limits by amount, partial payments |
| Workflow | Documents are metadata only; policy number is an unvalidated reference | Blob storage with virus scanning; a policy service lookup |
| Messaging | Relay assumes one instance (no row locking), no attempt cap, strict order (one stuck row blocks later ones); consumer runs in-process | Row locking (`UPDLOCK, READPAST`) or a lease, per-row dead-lettering, a separate consumer service |
| Messaging | Notifications are in-app only, with no read/unread state | Email/SMS channels, read state |
| Data | Outbox and idempotency rows are never cleaned up; claim numbers use a global sequence (gaps possible) | Retention jobs; per-year sequences if required |
| Reports | No USD total (FX non-goal); workload report not paged | Configured FX rates labelled illustrative; paging |
| API | `If-Match: *` unsupported; `/health` is liveness only; register/`POST /users` have no Idempotency-Key | Full RFC 9110 preconditions; a DB health check |
| Testing | Load-to-save race not tested deterministically (EF rowversion covers it); handlers tested end to end rather than with mocked EF; no frontend tests; no OpenAPI drift test | Concurrency tests, Angular component/router tests, a CI spec-diff check |
| Frontend | Generated models mark all fields optional; minimal styling; no i18n | `required` schema generation, a design system, localisation per market |
| Domain | No per-market rules or time zones (incident date allows UTC today + 1 day) | Market-specific rules and local dates |
